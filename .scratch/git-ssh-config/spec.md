# Git config and SSH workspaces — layout A

Status: resolved
Type: spec
Date: 2026-11-03

## Problem Statement

A developer uses different commit identities and SSH keys for work and personal repositories. Their settings are distributed across Git system/global/local configuration, conditional includes, repository overrides, and SSH configuration. Looking at one file does not explain the identity or key reference relevant to a particular repository.

The configuration inspected during this conversation already contains four remote-URL include conditions pointing to a work identity file, local identity overrides, and a repository-specific SSH command. Replacing this arrangement with a single global identity or an application profile could change working behavior. Existing open-source projects provide useful approaches, but the investigations found preservation, ordering, concurrency, or integration limitations relevant to this setup.

The developer wants to inspect and change this configuration inside Whichcraft, understand the source and impact of a change before writing it, and undo their change without removing another application's edits. The developer selected **A · Workspace** after trying a Whichcraft-style prototype, and explicitly requested functional `includeIf` management.

## Solution

Add **Git config** and **SSH** workspaces to Whichcraft's desktop shell, under Configuration between Environment and Developer tools. Use layout A and the existing visual system, navigation, dialogs, localization, and accessible controls.

In Git config, select a repository and see its effective commit identity, authentication-related configuration, and source precedence. Inspect behavior and all configuration, edit supported values in their actual source files, and create or edit conditional include rules. Preview rule matches and before/after identities across the repositories the user has selected.

In SSH, place the host list beside connection details and ordered identity-file references. Provide public-key metadata and source-file views, and connect these references back to Git configuration. Distinguish configuration evidence from a successful authentication result.

All supported changes follow **edit → preview → apply → read back → undo**. Initial writes cover existing Git identity/SSH-command entries, existing SSH IdentityFile entries, and adding/editing Git conditional includes that reference existing files. Other configuration remains inspectable and preserved. The production feature reads and writes real configuration through backend application services; the prototype remains an in-memory design reference.

## Implementation Decisions

- **Selected UI:** A · Workspace is the baseline. Git places identity and authentication cards beside source precedence; SSH places hosts beside connection and identity details. Keep Git Identity, includeIf, Behavior, and All configuration sections and SSH Hosts, Keys, and Config files sections. Source-file inspection remains available within A; B/C are prototype references rather than production layout options.
- **Terminology and scope:** Use the configuration terms in `CONTEXT.md` (Configuration Source, Occurrence, Commit Identity, Conditional Include, Repository Context, Impact Preview, Configuration Operation). A Tool Profile continues to mean a named set of Tool Installation Selections. Commit identity and conditional includes do not create an active Tool Profile. Configuration inspection is repository-aware, but it does not introduce per-project Tool Installation switching. This extends configuration management without changing ADR-0001's tool-selection policy. ADR-0007 records native-tool authority, no configured execution during inspection, and the separate configuration journal.
- **Architecture:** Follow ADR-0005. Rust domain types describe contexts, source records, diagnostics, plans, and configuration operation results without I/O. Application use cases orchestrate injected ports. Process, file, and journal adapters perform I/O. Tauri commands translate typed requests and delegate to application services. React uses immutable MVI state, pure reducers, and effects calling injected feature contracts; components do not invoke Tauri or read files directly.
- **One feature contract:** Add a narrow configuration service to application composition for Git and SSH. Reuse the established AppServices/transport/fake-service pattern rather than importing the legacy API singleton. The service owns context inspection, document inspection, planning, apply, and undo. Use separate internal Git and SSH semantics behind this shared operation boundary; do not create a generic replacement for every existing settings API.
- **Public operation contract:** Inspection returns explicit executable/repository context, source identity, scope, ordered occurrences, effective-value evidence, diagnostics, and editability. Planning accepts a typed intent and source occurrence/rule identity and returns an opaque plan identifier, dependency revisions, redacted diffs, and per-context impact with resolution status. Apply accepts the reviewed plan identifier and returns write status, readback status, and an undo operation identifier when applicable. Undo accepts an operation identifier and returns restored/conflicting/unverifiable outcomes. Backend validation remains authoritative; clients cannot submit unrestricted file replacements as Apply requests.
- **Executable context:** Resolve and identify Git from Whichcraft's existing Effective Installation/environment machinery where available. Build subprocess environments explicitly using the existing ProcessRunner approach and bind reads/plans to executable identity, fresh environment, repository location, and relevant configuration revisions. Selection, Effective Installation, and Shell Resolution remain distinct. Do not install Git or SSH automatically as a side effect of opening a workspace.
- **Git executable choice:** Default to Git's Effective Installation. The repository context bar lets the user pick another Git Tool Installation that Whichcraft has already discovered; it does not browse for arbitrary executables and does not change the Selection. Set no fixed minimum Git version; detect capabilities from the selected executable. Below Git 2.36, hide the remote-URL (`hasconfig:remote.*.url`) condition in the rule form and label existing remote-URL rules "not supported by this Git" without modifying them. Below Git 2.32 (no `GIT_CONFIG_GLOBAL`), disable impact preview with that reason; inspection and plain value edits still work. Base behavior on detected capability where a probe is practical and on version otherwise.
- **Repository selection:** Use explicit folder selection plus a remembered recent-repository list for impact comparison. Store only repository paths in `WhichcraftSettings`, never configuration content; cap the list (20 entries, most recent first), let the user remove entries, and show a path that no longer resolves as unavailable instead of dropping it silently. Discover repository, common Git directory, and worktree metadata through Git rather than assuming a checked-out folder contains a physical Git directory. Do not recursively inventory every repository on disk or reuse Scan Roots for repository discovery. Switching context keeps committed changes but invalidates dependent previews and ignores stale asynchronous responses.
- **Repository trust:** When Git refuses a repository for dubious ownership, say that Git is not reading that repository's local configuration, show the owner Git reports, and show the `git config --global --add safe.directory <path>` command for the user to copy and run themselves. Global, system, and included sources still display. Whichcraft never writes `safe.directory` itself, because it is a security setting, and never bypasses the check by reading `.git/config` directly.
- **Native Git resolution:** Native Git is authoritative for loaded scopes, active includes, origins, and effective values in a selected repository. Read configuration without pager or invoking helpers, aliases, SSH, hooks, filters, or editors. Preserve multivalue occurrence order and key-specific semantics, including empty credential-helper resets. Distinguish configured values, unset values, known defaults, and process overrides; do not invent an effective value from an incomplete inspection.
- **Git source model:** Keep physical source documents and ordered occurrences separate from resolved values. Identify system/global/local/worktree/command sources and include ancestry. Respect alternate global/system locations, XDG configuration, relative include targets, and home expansion. A local edit may affect sibling worktrees; surface that scope. Worktree-specific and command/environment sources are inspectable but not writable in this initial release.
- **Initial Git value editor:** Support existing user.name, user.email, and core.sshCommand occurrences in writable user global, local, or included files. Editing a repeated occurrence must not collapse other occurrences. System configuration is read-only. Behavior, helpers, signing, aliases, and unsupported settings are inspection-only; adding/deleting arbitrary keys and free-form whole-document editing are not initial requirements.
- **Conditional includes:** Provide creation in a chosen writable user global configuration file, appending after its current content with a visible ordering warning. The default target is the global file that exists; when both `~/.gitconfig` and the XDG file exist, default to `~/.gitconfig` and let the user choose the other. When `GIT_CONFIG_GLOBAL` is set, that file is the only global target. Edit existing supported rules in place in writable global or included user sources; includeIf rules in local repository configuration are read-only. Forms support hasconfig:remote.*.url, gitdir, and gitdir/i.
- **Folder conditions:** The folder form starts from a folder picker and converts its path to an absolute forward-slash pattern with a trailing slash, for example `E:\Work` → `gitdir/i:E:/Work/`. Default to `gitdir/i` because Windows paths are case-insensitive; the user may switch to `gitdir`. Show the exact condition text that will be written before preview. When editing an existing folder rule whose pattern lacks the trailing slash, warn that it matches only that exact Git directory, but do not change it unless the user does. Include targets may use existing absolute, home-relative, or source-relative paths. Resolve and validate the existing target; do not silently create identity files or rewrite all paths. Other native conditions remain preserved and inspectable, with explicit limits on match explanations.
- **Rule semantics:** Evaluate remote matching against any configured remote, not only origin. Preserve all existing URL-specific rules, even when they share a target. Multiple matched includes load at their declaration positions; later scalar values and local overrides can change the result. A matched condition and a changed effective identity are separate facts. A target included through a hasconfig remote condition must not introduce remote URLs directly or indirectly. Validation must use the installed Git's capabilities and report unsupported conditions without modifying them.
- **Impact previews:** Show before/after name and email, source changes, and match status for each repository in the current and recent-repository list. State that unlisted repositories may also be affected. Evaluate the candidate with native Git as follows:
  - Write the candidate document to a Whichcraft-owned temporary folder, never next to the user's file. Rewrite every relative or home-relative `path` and every `gitdir:./`/`gitdir/i:./` pattern in the copy to an absolute path based on the original file's location, so the copy means what the original would mean.
  - When the edited file is the global file, run Git with `GIT_CONFIG_GLOBAL` pointing to the copy. When the edited file is itself included, also copy its declaring files up to the global file and repoint each include path at the next copy.
  - Run each repository's evaluation from that repository with the same executable and environment as inspection. Map temporary paths in `--show-origin` output back to the original files before display.
  - Result status is `verified` when the evaluation ran this way. It is `unresolved`, with a reason, only when the copy cannot reproduce the original's meaning: a declaring chain outside global configuration, local or worktree sources as the edited file, a construct the rewrite does not understand, or a Git below 2.32.
  - Global edits, included-file edits under global, and remote-URL, gitdir, and gitdir/i rules must reach `verified` in the acceptance corpus. Never label an approximation as verified. The prototype matcher is not a production resolver.
- **SSH client choice:** Start from the client Git would use in the current repository context: `GIT_SSH_COMMAND`, then `core.sshCommand`, then `GIT_SSH`, then the `ssh` found on the selected Git's own search path. Name the client and list the files it reads: Windows OpenSSH reads `%USERPROFILE%\.ssh\config` and `%ProgramData%\ssh\ssh_config`; Git's bundled SSH reads `$HOME/.ssh/config` (HOME may differ from USERPROFILE) and `etc/ssh/ssh_config` under the Git installation. The user may switch between these two clients. When the command is a wrapper or a client that cannot be identified without running it, mark Git's client as unresolved and let the user pick which of the two clients' files to display.
- **SSH document model:** Preserve ordered Host/Match/Include structure, comments, repeated directives, and source locations. Resolve supported static Host patterns, negation, ordered includes/globs, and cumulative IdentityFile entries without flattening files. Scalar precedence follows SSH semantics rather than Git semantics. Unknown or dynamic Match conditions limit the result explicitly; avoid asserting a complete effective configuration when one may apply.
- **Initial SSH editor:** Edit a single existing IdentityFile occurrence in a writable user SSH source or included user file. Connection details such as HostName/User/Port, advanced directives, and system SSH sources are inspectable. Creating/deleting hosts, restructuring blocks, and editing arbitrary SSH directives are deferred. Preserve any complex block that cannot be edited reliably and explain its read-only status.
- **SSH inventory and Git references:** Derive host/key references from current source documents, not fixed display records. Read public-key files for algorithm/fingerprint metadata and check referenced path availability without reading private-key content. Public comments and filenames do not establish an account identity. Explain Git's configured SSH command and relevant environment overrides as evidence; do not execute an arbitrary wrapper or assume Windows OpenSSH and Git-bundled SSH share a client or agent. Refresh both workspaces after relevant source changes.
- **Read-only inspection has no configured execution:** Opening, refreshing, and previewing the workspaces must not authenticate, modify known-host trust, load keys into an agent, or execute commands from configuration. In particular, do not automatically run ssh -G on arbitrary user configuration because Match exec can execute a command. Native SSH may be used as a test oracle only against controlled fixtures without executable conditions. Unsupported dynamic configuration stays visible as unresolved.
- **Source-preserving edits:** Implement or adopt a source model capable of changing only the intended value or condition/path spans. Preserve untouched bytes, BOM, comments, blank lines, line endings including mixed endings, unknown directives, and duplicates. Validate the candidate before publishing. Unsupported encodings, malformed constructs, or ambiguous targets remain readable where possible but are read-only; never silently normalize or discard them. The writer choice must pass the acceptance corpus before real-file use.
- **Plan validity:** Preview is not an Apply. Bind a plan to source occurrences and all context/files that determine its diff and impact. Changing a draft, context, relevant file, or executable invalidates it. Recheck dependencies before writing and require a refreshed explicit review after a mismatch. A refreshed preview must not silently retarget a different occurrence or include rule. Configuration changes made by another application remain intact.
- **Single-file transactions:** Each initial operation changes one existing configuration file, including an includeIf block's condition and path together. Serialize conflicting writes and use the existing write-coordination pattern with configuration-specific scopes; do not reuse registry-only messages or revision bindings as file-operation contracts. Configuration writes join the coordinator's existing single active write: while one runs, Environment and Tools writes are refused with the usual busy message, and the reverse. Do not add a second, parallel lock. Git/SSH refreshes and context changes must respect pending operations. Integrate with current tool/environment invalidation when executable or environment context changes, without introducing unrelated write restrictions.
- **Publication and readback:** Prepare and validate replacement content separately, acquire the target's operation guard, recheck the current file, and publish using a Windows-capable replacement that keeps the target's existing owner and ACL. A replacement that would inherit the folder's ACL instead is a failure, because Windows OpenSSH rejects an SSH config with loose permissions. Keep unrelated data unchanged and report permission/lock/validation failures without claiming success. Read back disk content and effective results after publication. A failed readback is distinct from a failed write; an unexpected result must not trigger a blind whole-file restore over external edits.
- **Undo and interrupted operations:** Record a minimal durable configuration operation journal before publication, with operation identity, target identity, preconditions, and the exact before/after edit. Offer Undo for the latest successful configuration operation: one latest operation shared by Git config and SSH, available after a restart, one level only. After an Undo, the previous operation does not become undoable. Undo reverses only that edit after checking context and uniqueness; unrelated later edits survive, and a changed or ambiguous target causes a conflict. Detect pending/uncertain operations after restart and inspect current bytes before deciding their status. Surface them in a recovery banner that follows the existing Environment recovery banner's pattern. Existing environment/tool journals and their Undo semantics are not repurposed as arbitrary file journals.
- **Sensitive data:** Start from the name-based detection rules in `src/lib/secrets.ts` (`resolveSecret`) and extend them for configuration: URL userinfo (`https://user:token@…`), `http.*.extraHeader` and other header keys, and credential-bearing command arguments. Apply them to configuration keys as well as values. Redact in the backend before data crosses the transport, so the UI never receives the secret; share the rules with the frontend rather than keeping two drifting lists. UI diff redaction must not change the actual write payload. Do not log raw configuration, private keys, or full secret-bearing command lines. Journal only the material required for the operation, protect that local material, and exclude it from ordinary diagnostics. Do not copy unrelated file contents into a permanent operation history.
- **Interaction and delivery:** Reuse Whichcraft's tokens, components, navigation conventions, translations, loading/error states, and dark/light themes. Keep dialogs usable at the existing minimum window size, focus predictable after navigation/modals, and controls labeled and keyboard reachable. Production routing must mount the real workspaces; do not ship the fixture engine or layout/case switcher as the feature.
- **Upstream strategy:** No fork or new upstream dependency was selected in the conversation. Treat the five investigations as evidence for implementation choices, not authorization to replace the app with an upstream project. The externally visible contracts and acceptance corpus are fixed by this spec; parser/writer implementation may reuse suitable code or libraries after checking preservation behavior, licensing, Windows behavior, and dependency cost. No fork-versus-own-engine research stage blocks implementing these contracts.

## Testing Decisions

- **Confirmed seam:** On 2026-11-03 the user chose “API as the primary seam, plus important UI flows.” Drive inspection → plan → apply → readback → undo through the configuration application's public contract. Prefer this single behavioral boundary over separate tests of parser token internals, reducer branches, and adapter call ordering.
- **What a good test proves:** Assert returned source/effective-value evidence, visible diagnostics, exact resulting file bytes, lack of unintended writes, and conflict behavior. A correct output and unchanged unrelated content matter; a particular internal function call or data structure does not. Use deterministic fixtures and operation IDs where needed without mirroring implementation details.
- **Prior art:** Follow the existing application App tests for injected ports and plan/apply/undo behavior, failure-contract tests for controlled I/O failures, and desktop-shell Environment workspace tests for service-injected user flows. Follow write-coordination readback/cross-workspace tests for stale responses and refresh admission. Extend the existing frontend architecture and Rust application-layer checks when introducing feature contracts and adapters. These are patterns to reuse, not a requirement to build duplicate suites at every layer.
- **Real I/O within the primary seam:** Run application/API scenarios against temporary configuration files and repositories, an isolated HOME/global/system/XDG setup, explicit process environments, and identified native executables. Keep all fixtures inside owned temporary roots. Never read or mutate real user configuration, private keys, registry settings, known_hosts, credentials, or agents in these tests. Use no network authentication. Do not let inherited Git command-config variables contaminate fixture results.
- **Git acceptance corpus:** Cover system/global/XDG/local precedence; separate origins for name/email; all four investigated remote URL forms; multiple remotes where only a non-origin remote matches; no-remote repositories; multiple matching includes in declaration order; inactive includes; relative/home include paths; include cycles, missing targets, and invalid syntax; hasconfig remote-target restrictions; folder boundaries and case sensitivity; local override after a matched rule; accumulating helpers with resets; alternate config locations; linked worktrees and shared-local scope; switching Git executable/context between inspection and Apply; a repository refused for dubious ownership (explained, global sources still shown, no `safe.directory` write); and capability gating, using an older Git where one is available and a capability fake otherwise.
- **Impact preview corpus:** Candidate evaluation reaches `verified` for a global edit, an edit to a file included from global, relative and home-relative include paths, and a `gitdir:./` rule, with results equal to native Git after the change is applied for real. Origins shown in preview name the original files, not temporary copies. A local-source edit reports `unresolved` with its reason. Preview leaves the user's folders free of new files.
- **Rule and edit flows:** Add and edit supported include rules, verify exact condition/path diff and per-repository outcomes, preserve rule position, and undo the operation. Verify folder-picker conversion (`E:\Work` → `gitdir/i:E:/Work/`), the `gitdir` alternative, and the trailing-slash warning on an existing rule. Verify editing each supported existing Git occurrence and one SSH IdentityFile occurrence. Show read-only behavior for unsupported conditions, protected/system/worktree sources, absent editable occurrences, and unproven encodings. Preview/cancel must leave live file bytes unchanged.
- **SSH acceptance corpus:** Cover overlapping exact/wildcard/negated Hosts, first-value scalar behavior, repeated IdentityFile ordering, included files and glob order, missing include/key paths, public-key metadata, unsupported directives preserved, and unresolved Match conditions. Include a Match exec fixture whose command would create a sentinel file and assert that inspection/preview never creates it. Compare fully supported static fixtures with a native SSH client identified in the result; these oracle fixtures must have no executable or network-dependent conditions. Cover client choice from `GIT_SSH_COMMAND`, `core.sshCommand`, `GIT_SSH`, and the default, the file set each client reads, an unidentifiable wrapper reported as unresolved, and switching clients.
- **File preservation and failure cases:** Compare bytes for UTF-8 with/without BOM, LF/CRLF/mixed endings, inline comments, duplicates, unknown entries, and trailing content. Inject permission failures, locked targets, failed publication, and failed readback. Verify the target's owner and ACL are unchanged after Apply and Undo, using a fixture with an explicit non-inherited ACL. Verify changed dependencies block Apply; a refreshed preview keeps the intended target; unrelated changes survive Undo; same-target changes and ambiguous duplicates block Undo; and restart recovery classifies before/after/unexpected target content without overwriting it. Verify the operation journal does not retain unrelated secret-bearing content.
- **Cross-workspace/API cases:** Changing SSH key references refreshes Git's explanation; changing Git SSH-command references does not alter the SSH host file; relevant executable/environment changes invalidate plans; late reads for an old repository do not replace current results; repeated Apply cannot publish the same plan twice; a configuration write refuses a concurrent Environment or Tools write and the reverse; Undo after a restart reverses the latest configuration operation from either workspace and offers no second level; the recent-repository list survives a restart, stores no configuration content, and marks a removed folder unavailable; and configuration operations leave Tool Installation Selection and Tool Profiles unchanged.
- **Focused UI cases:** Render the real desktop shell through injected services and exercise navigation into Git config/SSH, repository/host selection, layout A summaries and origins, an identity edit, a rule match with a local override, review/cancel/apply/undo, and a conflict with explicit refresh. Check source edit controls and disabled/read-only explanations. Avoid repeating the full parser/native-process corpus through the browser.
- **UI quality and completion:** Check dark/light themes, keyboard/focus behavior, dialog scrolling and readable diffs at the current minimum window size. Run the existing accessibility/Storybook tooling for the new states after transitions settle. Run applicable frontend type/build/lint checks, architecture checks, Rust application/adapter checks, and the native fixture acceptance scenarios. Clearly identify unavailable native capabilities instead of silently counting skipped scenarios as passed.
- **Evidence boundary:** Existing prototype walkthroughs and native Git probes support the design, but they are not production acceptance tests. Completion requires the production contract and real-file adapter flows above. No tests are added or run merely to validate this Markdown specification.

## Out of Scope

- Tool Profile integration, active identity profiles, per-project Tool Installation switching, changing PATH, installing Git/SSH, or changing existing installation-management policy.
- Forking any of the researched projects, adding a Go sidecar, replacing the desktop shell, or promoting the throwaway prototype parser/matcher into production by default.
- Creating/deleting identity files, hosts, arbitrary Git keys, or SSH blocks. Include-rule creation and editing are included; rule deletion/reordering is deferred. Free-form configuration editing and transactions spanning multiple files are deferred.
- Writing system configuration or adding UAC workflows. Editing worktree-specific configuration or modifying the worktree extension. Reading and explaining these sources remains in scope.
- Form editing for onbranch or other conditional-include types beyond the three selected conditions, and a complete hand-written implementation of every Git/OpenSSH resolution rule. Preserve unknown constructs and show resolution limits.
- Editors for Git behavior, signing, aliases, hooks, credential helpers, and advanced SSH options. These remain inspection-only in the initial feature.
- Key generation, private-key viewing, passphrase changes, key deletion, adding/removing agent identities, agent service control, and enrolling keys with hosting services.
- Hosting-service login/account management, credential-store inspection or migration, connection/authentication tests, SSH sessions, tunnels, proxy execution, and changes to known_hosts or host-key verification.
- Machine-wide repository scanning, proving server account ownership, proving which key a server accepts, configuration sync/import/export, remote backups, and an unlimited configuration history.
